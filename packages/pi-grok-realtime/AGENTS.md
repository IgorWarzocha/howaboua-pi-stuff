- `credentials.ts` matches the selected access against Pi's active xAI auth: save uses offline status plus `isUsingOAuth`; start also checks the canonical resolved `source`. Pi's public registry cannot select a nonactive credential. `apiKey` is a transport bearer, not login-type evidence. Native and LAN audio never receive credentials.
- `session.ts` owns xAI wire sequencing; `controller.ts` owns voice lifecycle; `controls.ts` serializes microphone ownership across voice and dictation. Resume the socket without closing or transferring the audio owner. Idle voice requests use user-message kickoff so the full extension preparation chain runs.
- xAI server VAD cancels interrupted responses itself, sometimes without `response.done`. Retire them on `speech_started`; late completion cannot own a newer turn. Do not send a second `response.cancel`.
- Pi updates use Grok Bot's seeded function-call/output history pair, not system conversation items or mutable prompt data. Keep session updates complete so tools, voice and audio configuration travel with the current Pi state. Provider responses can overlap: continuation waits for active responses and actual playback drain, not just generation completion.
- Validate offline with disposable protocol probes. Live voice, microphone, LAN, account-mint and RPC checks require separate user authorization.
- Do not invent audio, text, context, timeout or settings caps. A limit needs concrete Grok Bot provenance; keep wire integrity and platform validation distinct from product limits. A Grok Bot harness limit does not automatically belong in the Pi task handler.
