Write for the user. A developer tool still has users, and its README is part of the product. Save the codebase tour for contributor or internal documentation.

A README should let the reader understand the offer, recognise whether it fits, reach a real result, operate normally, and recover from likely failure. Put the common path and defaults before advanced configuration, migration, limitations, and troubleshooting. Link deeper references instead of swallowing them all.

Earn claims through mechanisms, commands, behaviour, visible results, or removed friction. State major requirements, deliberate exclusions, trust boundaries, permissions, and failure modes early enough to affect the decision. Own recommendations as product judgment or lived experience. Let humour expose a trade-off, boundary, or warning rather than decorate the page.

Warm framing and crisp procedure can coexist. Product voice belongs in openings, recommendations, transitions, and warnings. Commands, settings, and recovery steps must remain literal enough to follow without interpreting a mood.

Keep README detail user-visible: installation and removal, requirements, first launch, modes, defaults, configuration precedence, status, errors, migration, limitations, and recovery when those matter. Keep module ownership, internal call paths, source layout, build architecture, and implementation rationale elsewhere. Add contributor setup only when the project intentionally invites it.

Structure should expose decisions. Use headings that match the reader's next question, keep commands beside their observable outcomes, and use numbered steps only for real sequences. Tables earn their place when rows repeat the same decision fields. Dense is acceptable when every section answers a real user question. Short is not a virtue when ordinary operation requires source archaeology.

Choose the document's dominant job. A tutorial reaches an early result, a how-to completes a task, a reference exposes facts and limits, and an explanation builds one bounded mental model. Mix them only when the reader's path remains clear.

Use exact symbols, commands, paths, flags, labels, and domain terms. Verify examples, outputs, defaults, and behavioural claims against the current product. Put proof after actions that need it and conditions or warnings before the actions they govern.

Stop when the reader can decide, begin, operate, and recover.
